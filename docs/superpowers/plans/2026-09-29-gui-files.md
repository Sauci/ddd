# The Project's Files Tab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Files tab listing the project's `includes`, from which a reader creates a file, adds an existing one, and removes one — a removal judged by the analysis itself.

**Architecture:** The tab reads each `includes` entry with the loader's own public rule, `expand_include`, and joins it on the page to the `State.files` it already receives. Plans for the three actions live in a new `ddd.file_plans`; the one creation recipe the repository repeats is extracted first so this part is not its third copy. The loader gains one override — the root's `includes`, for one analysis — through which the session re-runs exactly the runs a revision was made from, and a removal is refused where that finds errors the project does not have now.

**Tech Stack:** Python 3.14, pydantic v2, pytest at 100 % line and branch; React 19 + TypeScript, Vitest at 100 % over `src/api`, `src/lib`, `src/state`; Playwright journeys; Ladle stories with Docker screenshot references; Sphinx docs under `-W`.

**Spec:** `docs/superpowers/specs/2026-09-29-gui-files-design.md`. Read it before any task. Where this plan departs from it, the departure is a ruling in *Rulings taken* at the end, with its reason.

**As built.** The task texts below are the plan as written before execution, and are left so. Execution departed from them in places - the judge's matching most of all, redesigned four times, each time on a project a reviewer built - and every departure is a row of *Rulings taken*, whose rows 8 on record what was built instead. Read a task's code as what was planned, the table as what was done. Three sentences false when they were written are corrected where they stand, each saying so.

## Review Focus

The five inputs most likely to bite a person using this tab that no task's happy path reaches. Each is pinned by a test in the task that owns it.

1. **Removing a file from a project that does not load** (Task 3, Task 5). The analysis is skipped whenever loading reports an error, so "now" has only load errors and every semantic error elsewhere is masked. Removing the broken file would reveal them as "new" and refuse the one removal the reader most likely wants. The judge compares only when the revision was analysed; otherwise the removal is allowed and says it could not be judged.
2. **A project with cmake build records** (Task 3). The session analyses through each build's own `run_build`, with that build's severity flags. The judge must re-run *those* runs with the override, or "before" and "after" differ for a reason other than the removal.
3. **A later entry's finding after a removal** (Task 3). Removing entry 2 moves entry 4 to 3, so an `include-empty` already at `project.includes[4]` would read as new at `[3]`. A finding on the root's own entries is keyed by the entry it names.
4. **An entry whose file was deleted** (Task 4, Task 5). An entry naming no existing file names nothing: a plain path is that missing file, reported `file-not-found`, and one holding a wildcard is a pattern matching nothing, reported `include-empty`. The row must show it as naming nothing, carrying its finding, and Remove must still take it out. *(Corrected at close-out: this item first read "by the includes rule, an entry naming no existing file is a pattern", false for a plain path - measured in Task 4's pre-flight.)*
5. **Adding a file a pattern already pulls in** (Task 4). Refused, naming the pattern — not added a second time as a literal.

```python
def appended_at(listed: object) -> int:
    """Where a new entry lands: at the end of a list read off disk, or at the front of a value
    that is not a list at all - which the edit engine then refuses with a sentence of its own,
    rather than this guessing at a position inside something that holds none."""
    if isinstance(listed, list):
        return len(listed)
    return 0


def created_beside(
    project: Path, filename: str, text: str, cache: dict[Path, Document]
) -> tuple[PlannedEdit, PlannedEdit]:
    """The one shape a file is created in: beside ``project``, laid out as a person would write
    it, and appended to ``project``'s own ``includes`` in the same plan.

    The only creation :func:`ddd.gui.session._confined` allows - beside the description, by an
    edit that adds it to the includes there - so a plan built any other way is refused when it
    is applied. :func:`adopt_units`, :func:`ddd.shared_plans._created` and
    :func:`ddd.file_plans.create_plan` all create through this, and cannot drift apart.
    """
    laid_out = lay_out(text, one_line=False, indent="", unit=DEFAULT_INDENT_UNIT, newline="\n")
    includes = read(project, cache).value_at("project.includes")
    return (
        PlannedEdit(
            project.parent / filename, (Operation("set", "", f"{laid_out}\n"),), creates=True
        ),
        PlannedEdit(
            project,
            (Operation("insert", f"project.includes[{appended_at(includes)}]", _raw(filename)),),
        ),
    )
```

Move `_appended_at`'s docstring reasoning here rather than losing it. Replace `adopt_units`' create arm and `shared_plans._created`'s tail with a call, each still sorting the two edits by path. Delete `shared_plans._appended_at`, and import `appended_at` wherever it was used.

- Produces: `finding_identity`; `findings_with(revision, includes) -> tuple[Filed, ...]`, a module-level function of `ddd.gui.session`; `new_errors(project, before, before_includes, after, after_includes) -> tuple[Pair, ...]` over `(path, diagnostic)` pairs.

```python
_ENTRY: Final = re.compile(r"^project\.includes\[(\d+)\]$")


def new_errors(
    project: Path,
    before: Sequence[Pair],
    before_includes: Sequence[str],
    after: Sequence[Pair],
    after_includes: Sequence[str],
) -> tuple[Pair, ...]:
    """The errors ``after`` has that ``before`` does not, in ``after``'s order: what a change of
    the root's ``includes`` would break.

    Errors only, after each run's severity policy: the line ``ddd check`` draws between a
    project that passes and one that fails. A warning a removal brings is the reader's to see
    after applying it, not a reason to refuse. Written as loops rather than comprehensions with
    a filter, which coverage.py counts no branch in.
    """
    had: set[tuple[object, ...]] = set()
    for _, diagnostic in before:
        if diagnostic.severity is Severity.ERROR:
            had.add(_key(diagnostic, project, before_includes))
    fresh: list[Pair] = []
    for found in after:
        if found[1].severity is not Severity.ERROR:
            continue
        if _key(found[1], project, after_includes) in had:
            continue
        fresh.append(found)
    return tuple(fresh)


def _key(diagnostic: Diagnostic, project: Path, includes: Sequence[str]) -> tuple[object, ...]:
    """What makes two findings the same one across a change of ``includes``:
    :func:`ddd.lsp.diagnostics.finding_identity`, save that a finding on one of the root's own
    entries is keyed by the entry it names rather than by its position - removing an entry moves
    every later one up, and the same finding would otherwise read as new."""
    location = diagnostic.location
    if location is not None and location.path == project:
        entry = _ENTRY.fullmatch(location.pointer)
        if entry is not None:
            index = int(entry.group(1))
            if index < len(includes):
                return (diagnostic.check, diagnostic.severity, includes[index], diagnostic.message)
    return finding_identity(diagnostic)
```

Each nested `if` is its own statement on purpose: joined with `and`, coverage records one branch pair for the whole condition.

```python
CREATABLE: Final = ("component", "types", "units", "constants", "sections", "rasters")
"""The kinds a reader may create a file of here, in the order the chooser offers them. Not
``project``: a sub-project's own includes belong to opening it, and are out of this tab's
reach (spec §6)."""

FILE_NAME: Final = re.compile(r"[A-Za-z0-9_-]+")
"""A name a new file may take, before ``.ddd.json`` is added: letters, digits, ``_`` and
``-``. No separator, so a file can only ever be created beside the description, and no dot,
so the suffix is always the one every project committed to this repository uses."""


class FileRefusalError(Exception):
    """A change of the project's files that is not made, and why - as the other plan modules'
    refusals: ``code`` is ``not-found``, ``invalid`` or ``unreadable``."""

    def __init__(self, code: str, message: str) -> None:
        super().__init__(message)
        self.code = code
        self.message = message


@dataclass(frozen=True, slots=True)
class IncludedEntry:
    """One entry of the root's ``includes``, as the loader's own rule reads it."""

    index: int
    entry: str
    names: bool
    """Whether the entry names an existing file, and so is that file whatever it spells. An
    entry naming none is a pattern, possibly one matching nothing."""
    key: Path
    """``parent / entry`` resolved: what a route and the page select this row by."""
    files: tuple[Path, ...]


def included_entries(project: Path, cache: dict[Path, Document]) -> tuple[IncludedEntry, ...]:
    listed = read(project, cache).value_at("project.includes")
    found: list[IncludedEntry] = []
    if not isinstance(listed, list):
        return ()
    excluded = {resolve_path(project)}
    for index, entry in enumerate(listed):
        if not isinstance(entry, str):
            continue
        key = resolve_path(project.parent / entry)
        try:
            files = tuple(expand_include(project, entry, excluded))
        except (OSError, ValueError, NotImplementedError):
            files = ()
        found.append(IncludedEntry(index, entry, key.is_file(), key, files))
    return tuple(found)
```

## What was left open

Filled in as the work goes. Each entry says what was not done and what it costs.

- **Reordering `includes`.** Order decides which of two files declaring one name carries the `duplicate-*` finding, and which file of a vocabulary an add appends to, so reordering has consequences a reader should see previewed. Its own piece of work.
- **A sub-project's own `includes`**, and creating a sub-project. Managing them is opening it as a project.
- **Creating a file in a subdirectory.** `_confined` allows beside the description only; widening it is a security change.
- **The judge's one way to allow a new error.** Counting per place, a new error hides only where an
  error of its check and severity leaves the same place - with the same message, where the place is a
  whole file or none - or where it has the shape of a mirror. ddd's own `definition-mismatch` reaches it
  where a build lowers `duplicate-component` or `duplicate-type`: removing the first declaration lets the
  dropped one load, and a reader's disagreement changes what it is about while its place stays. Under
  the default severities no case was found. Stated in `ddd.file_plans.new_errors`' docstring; closing it
  means keying that check by its wording, which refuses the removal the tab most needs - one of two
  writers ending their conflict.
- **Harmless removals the judge refuses.** A move of a finding ddd places by an order a removal can
  change: a file the root and a sub-project both list, the root's entry removed; the first read
  declaration of a colliding or case-similar name gone; a relabel or a re-count against a new owner. Each
  refusal quotes an error the project would really have.
- **A create is not judged.** The file does not exist until the edit is made. A build raising
  `empty-vocabulary` or `empty-component`, or a plugin's check, can make a create fail unannounced.
- **`ddd gui` does not notice a file a pattern newly matches** until another watched file changes - a
  limitation older than this branch, filed as its own task. The judge refuses such a judgement as stale
  meanwhile.
- **Routes that lead nowhere.** `file-not-found` at a root entry routes nowhere: it is a load check, and a
  file carrying one counts as not loaded, so `route_of` answers `None` before any arm. A
  sub-project's `include-empty` or `empty-vocabulary` routes to a key no row holds, and opens the tab with
  nothing selected.
- **New file lists a file twice** where a pattern or a missing entry already names it: `_confined` accepts
  a created file only where the edited includes name it literally. The loader reads it once.
- **Names that can differ.** An undo label under a symlinked directory names where the link leads; a
  removal's panel title and its undo label can spell one file two ways (`a.ddd.json`, `./a.ddd.json`).
- **An over-long file name** passes the preview and is refused `unwritable` at apply, nothing written.
- **Two deferred minors:** no test of `adopt_units` itself with a non-list `includes`; the second
  operand of `_load_project`'s override condition pinned by a crash rather than a named test.
- **Filed separately, older than this branch:** `_check_local_reference` lets load order decide whether a
  reference is reported where two components declare one name local, against its own docstring.
