**C1, confirmed, Critical kept** (`p9/c1/c1.txt`, `p9/c1/c1_controls.txt`, `p9/c1ex/c1ex.txt`).
- My project: `Prod` writes `Count` and `Buf`, and `Cons` reads them. I widened `Count` from
  `uint8` to `uint32` and grew `Buf` from `[4]` to `[8]` in both descriptions. `prod.c` now writes
  70000, and `cons.c` is not edited.
- One `ninja`, exit 0: it recompiles `prod.c` and `ddd_globals.c` and relinks. `Cons.h` already
  says `extern uint32_t Count` and `Buf[8]`, and the image prints `Count=112, sizeof(Buf)=4`.
- A second `ninja`, with nothing touched, says `output cons.c.obj older than most recent input
  Cons.h`. It recompiles, and the image prints 70000 and 8.
- Controls: `PROJECT` mode does the same. `MinGW Makefiles` builds right at once. A copy of the
  module whose generation names `Prod.h` and `Cons.h` as `BYPRODUCTS` builds right at once, and
  its next run is `no work to do`. So the cause is the undeclared headers under Ninja.
- The shipped `examples/cmake`, from a copy, with `ValueJ` from `uint8` to `uint16`: one `ninja`
  recompiles only `ddd_globals.c`. `event_logger_step` still stores `mov %dl` into a 2 byte
  variable, and only the second build gives `mov %dx`.
- Critical stays. The image's code disagrees with its globals and its a2l after an exit-0
  incremental build, and that is the build the pages describe.

**I5, confirmed with a correction** (`p9/i5/i5.txt`, `p9/i5/i5_331.txt`).
- What holds: under `Müller-project` in `PROJECT` mode, with `cmake_minimum_required(VERSION
  3.30)`, configure exits 0 and Ninja then stops on `M├╝ller-project/src/p.ddd.json ... missing`.
  The console code page is 850, and `ddd sources` writes the UTF-8 bytes `303 274`.
- The correction: the same tree with a 3.31 minimum builds. CMake's own help on
  `execute_process` says UTF-8 is the default `ENCODING` "since CMake 3.31" (policy CMP0176),
  and AUTO before that. So the trigger is a project whose minimum is below 3.31, and every real
  CMake from 3.15 to 3.30.
- Important stays. The 3.30 minimum is the one the shipped example and the page's own recipe
  write (`docs/build_integration.rst:125`). A user under `C:/Users/André/` who follows them
  cannot build, and the error does not point at the cause. The one-line fix the pass proposes
  stands.

**M5, confirmed with a correction** (`p9/m5/m5.txt`).
- What holds: a `PROJECT` in the build tree that is generated later, and a `PROJECT` with a JSON
  syntax error, each print "the generation will depend on that file alone". Each then stops
  configure: `file failed to open for reading`, or `has neither a project nor a component name`.
- The correction: the fallback is not dead. A root that parses and fails the schema
  (`"includes": 5`) prints the same line, and configure exits 0 with the project file as the
  only dependency. Pass 19 I2's raising plugin model reaches the same fallback.
- So the dead part is the two cases the comment at `cmake/Ddd.cmake:122-123` names: "cannot be
  read yet". The pass's change (remove the sentence, the status line and the tolerance) would
  remove a branch that runs. Say instead that the file has to exist and parse at configure.
