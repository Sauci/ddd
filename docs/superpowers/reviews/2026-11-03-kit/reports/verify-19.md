**I3, confirmed for a document on stdout, lowered to Minor** (`p19_i3_pipes.txt`,
`p19_i3_wsl.txt`, `wsl/i3_main.py`, `wsl/run_i3.sh`).
- What holds: on Windows under `set -o pipefail`, a project of 8,000 errors exits 1 alone, but
  `check --format json | head -1` exits 0 in 5 runs of 5, and so does `dump | head -1`. A project
  of 6 errors, whose report fits in the pipe, exits 1.
- On Linux I took the real `main` and `_write_utf8` out of a copy of `cli.py` with `ast` and ran
  them in WSL's python 3.12, with a handler that prints the way `_report` does. A json document
  cut by `head -1`, or with its reader gone (`| true`), exits 0 in 10 runs of 10.
- What does not hold: the text report on stderr. `check 2>&1 | head -1` and `| head -50` exit
  120 in every run, on Windows with the real tool and on Linux with the real `main`. The
  `BrokenPipeError` clause points stdout at the null device and returns 0. Stderr's unwritten
  buffer then fails again when the interpreter exits, and python's exit code becomes 120. The
  pass's 0 for a cut text report came from an in-process stream, which never reaches that exit.
- So the pass's CI example, `ddd check p 2>&1 | head -50` under GitHub's `pipefail`, fails rather
  than passes. A failing verdict reads 0 only when a reader stops early on the json report, the
  dictionary or a listing. `SPEC.md:2183-2185` even states that 0 for "a reader of the tool's
  standard output that stops reading", which contradicts its own "findings (1)" two lines above.
- Lowered to Minor: the trigger left is a reader that stops early on a document, which is rare
  in a gate. The exit code still depends on stream and platform (0, 1, 2 or 120), as filed.
  Pass 9 M1 found the 120 and the 2 of the same clause; this adds the 0 of a failing run.
